# LangGraph 控制流深挖：为什么用图、状态怎么收敛、循环怎么终止

## 1. 一句话回答

因为旅行规划不是线性流程，而是有并行搜索、条件路由、质量门禁和重试的复杂工作流。图把控制流和数据流显式化：节点只负责一件事，边决定下一步，状态是共享契约；循环不是随便转，而是带失败原因、有重试上限、能降级退出。

## 2. 为什么用图编码，而不是直接写循环

### 2.1 控制流和数据流解耦

- 节点只做业务：需求解析、景点搜索、行程编排、预算审核、质量校验。
- 边只做路由：成功走下一步，失败带 feedback 回到行程节点。
- 直接写循环时，业务逻辑和 `if / while / break` 混在一起，改动一个条件容易影响整段流程。

### 2.2 支持并行和汇合

景点、美食、酒店、天气互不依赖，可以并行执行，再统一汇合到行程编排节点。直接写循环要么串行变慢，要么自己维护线程/协程和汇合逻辑。

### 2.3 可观察、可调试

每个节点执行完都可以上报进度和状态。出问题时能定位到具体节点，而不是只知道“整个函数挂了”。旅行项目的 SSE 进度就是按节点推送的。

### 2.4 可测试、可替换

每个节点可以单独测试，例如只测预算节点、只测质量节点。以后要把 DeepSeek 换成别的模型，或者新增租车 Agent，只需要改对应节点和边。

### 2.5 可扩展和可恢复

图可以加 checkpoint、human-in-the-loop、失败重放和断点恢复。直接写循环很难做这些。

### 2.6 什么时候不该用图

如果任务只是“调一次模型 -> 返回结果”，用图反而增加复杂度。图适合：多步骤、有分支、有并行、需要校验和重试的任务。

## 3. 状态怎么收敛

### 3.1 状态是显式的共享契约

旅行项目用 `AgentState` 承载：

- `request`：用户请求
- `requirement`：需求分析
- `attractions / foods / hotels / weather`：并行搜索结果
- `plan`：当前行程
- `feedback`：上次失败原因
- `retry_count`：重试次数
- `current_plan / instruction`：调整场景
- `nearby / routes`：周边和路线
- `invalid_days`：质量校验定位到的问题天数
- `weather_policy`：天气风险日和室内/室外编排策略

节点只返回自己负责的字段增量，由 LangGraph 合并。并行节点写不同字段：景点写 `attractions`、美食写 `foods`、酒店写 `hotels`、天气写 `weather`，所以不会互相覆盖。

如果两个并行节点要写同一个字段，就必须定义 reducer 或冲突合并规则，否则状态会不确定。

### 3.2 收敛条件是可验证的断言

旅行项目的收敛不是“模型说好了”，而是三个硬条件：

1. 预算：`total_cost <= budget`
2. 质量：景点/餐厅来自候选池、坐标可用、天数匹配、每天有景点和餐厅
3. 路线：每天从酒店出发、回到酒店、每段有轨迹

三个条件都通过，状态才算收敛。

### 3.3 每次失败都把具体原因写回状态

例如预算失败：

```text
当前 total_cost 超过预算，请重新编排，确保 total_cost 不超过预算。
```

下一次 itinerary 节点读取 `feedback`，带着具体约束重新生成。没有 feedback 的重试是盲目重试，容易一直不收敛。

### 3.4 工程上的“收敛”不等于数学证明

LLM 不保证一定满足约束，所以工程上要接受两种退出：

- 满足约束：正常收敛，进入下一节点或 END。
- 达到重试上限：带警告交付，而不是无限循环。

提高收敛概率的方法：

- feedback 具体化，不只说“失败”。
- 限制动作空间，例如景点只能从高德候选池选择。
- 加确定性修复，例如坐标缺失自动从候选池补齐。
- 必要时放宽非关键约束，例如景点数量、餐厅数量。

## 4. 循环怎么终止

### 4.1 有界重试

条件边只在“失败且 retry_count < 3”时回退；能定位到具体天数的问题走局部修复，其他走整段重排：

```text
budget 失败 -> feedback + retry_count + 1 -> itinerary
quality 失败且能定位到第 N 天 -> repair_days -> budget -> quality
quality 失败但无法定位天数 -> feedback + retry_count + 1 -> itinerary
route 不闭环 -> feedback + retry_count + 1 -> itinerary
通过或 retry_count 到上限 -> 继续下一步 / END
```

`retry_count` 单调递增，所以循环一定终止。

### 4.2 当前项目是全局重试预算

预算、质量、路线三个阶段共享同一个 `retry_count`，语义是“整条生成链路最多重试 3 次”，不是每个阶段各 3 次。

如果想做阶段级控制，可以拆成：

- `budget_retry`
- `quality_retry`
- `route_retry`

这样每个门禁独立重试，但总迭代次数可能变大，必须同时加总上限。

### 4.3 生产环境还要加的保护

- 总迭代上限：防止多个阶段各自重试导致总次数过多。
- 超时上限：例如 60 秒还没完成就降级返回。
- Token / 成本预算：防止重试消耗过多。
- 异常中断：外部 API 连续失败时熔断或降级。
- Checkpoint：已经接入 `SyncMemorySaver`；每次任务用 `thread_id` 隔离，重启进程前可以恢复未完成的图状态。

## 5. 对应你的 graph.py

| 代码 | 作用 |
| --- | --- |
| `AgentState` | 定义共享状态字段 |
| `analyze_node` | 需求解析 |
| `attraction_node / food_node / hotel_node / weather_node` | 并行搜索 |
| `itinerary_node` | 读取 feedback 重新编排 |
| `budget_node` | 预算校验，失败写 feedback |
| `quality_node` | 质量校验，失败写 feedback |
| `repair_days_node` | 只重生成问题天数并合并回原计划 |
| `surrounding_node` | 路线闭环校验 |
| `route_after_budget / quality / surrounding` | 条件边决定回退还是继续 |
| `SyncMemorySaver(checkpointer)` | 用 `thread_id` 保存和恢复图状态 |
| `retry_count < 3` | 有界重试，保证终止 |
