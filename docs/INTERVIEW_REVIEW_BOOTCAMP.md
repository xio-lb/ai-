# AI 旅行规划助手 · 面试复习训练营

> 使用前提：你已经有 `docs/INTERVIEW_GUIDE.md` 这份资料库。
> 本训练营解决的是“资料太多，背不下来，讲不出来”的问题。

---

## 1. 训练目标

面试结束前，你要能做到三件事：

1. **30 秒**把项目讲成一个正常人听得懂的产品。
2. **3 分钟**把架构、核心设计、难点、结果讲完整。
3. **10 分钟**顶住面试官追问，每一个“为什么”都能用项目里的代码和测试回答。

一句话判断标准：面试官听完后，知道这个项目是你自己做的，而不是你背了一篇教程。

## 3. 三份必背讲稿

### 3.1 30 秒电梯版

> 我做了一个 AI 旅行规划助手。用户说“我想去成都玩 3 天，预算 3000”，系统会自动搜索真实的景点、餐厅和酒店，排成每天能走的行程，在地图上画出闭环路线，还能切换交通方式、播放路线动画、记账、保存历史。技术上用 LangGraph 编排多个 Agent，后端是 FastAPI，前端是 Vue 3，已经部署上线。

### 3.2 3 分钟完整版

按这个顺序讲，不要跳：

1. **用户问题**：普通人想要一份“真的能执行”的旅行计划，而不是 AI 随便编一段文字。
2. **我的方案**：表单 + 对话收集需求，后端多 Agent 协作生成，前端地图展示和调整。
3. **数据流**：
   `用户需求 → 需求解析 Agent → 并行搜索景点/美食/酒店/天气 → 行程编排 Agent → 预算 Agent → 质量校验 Agent → 路线闭环 → 前端地图`
4. **关键设计**：
   - Agent 之间用共享状态，不互相聊天；
   - 景点只能从高德候选池里选，防止 AI 编造；
   - 预算超支和质量不过会带原因重试，最多 3 次；
   - SSE 实时推送生成进度；
   - 精准调整只改局部，不整段重生成。
5. **结果**：后端 30 个 pytest 通过，前端构建和冒烟测试通过，Vercel + Railway 自动部署。
6. **一句话收尾**：这个项目最大的收获不是功能多，而是学会了把不可控的 LLM 调用变成可控、可测试、可重试的工作流。

### 3.3 10 分钟深聊提纲

面试官开始追问时，按这六个板块走：

1. 架构与边界：为什么前后端分离？为什么 LangGraph？
2. Agent 协调：状态怎么设计？节点怎么分工？失败怎么办？
3. 可靠性：怎么防幻觉？怎么保证路线闭环？怎么降级？
4. 数据与性能：SQLite 够不够？缓存 TTL？SSE 为什么合适？
5. 工程质量：测试覆盖什么？部署怎么自动完成？
6. 演进：如果重做，架构改什么？当前最大短板是什么？

## 4. 名词大白话表

### 4.1 Agent 与工作流

| 名词 | 大白话 | 项目里对应哪里 | 面试怎么说 |
| --- | --- | --- | --- |
| Agent | 一个只负责某件事的“员工” | 需求解析、景点搜索、预算、质量等节点 | 每个 Agent 职责单一，只写自己负责的字段 |
| LangGraph | 管理这些员工和流程的“流程图框架” | `backend/app/agents/graph.py` | 用状态图显式建模流程，让 LLM 调用可观察、可重试 |
| 节点 | 流程图里的一个步骤 | analyze / attractions / itinerary / quality | 节点只负责一件事，输入输出都是结构化的 |
| 条件边 | 根据结果决定下一步走哪条路 | 预算超支回到行程节点 | 结果不满足条件就带原因重试 |
| 共享状态 | 所有员工共用的“工作台” | `AgentState` TypedDict | Agent 不互相发消息，只读写同一份状态，避免语义漂移 |
| 并行 | 互不依赖的事情同时做 | 景点、美食、酒店、天气同时搜索 | 数据采集节点并行，减少总耗时 |
| 任务分解 | 把大任务拆成小步骤 | 需求 → 搜索 → 编排 → 校验 | 先拆阶段，再决定哪些可并行、哪些必须汇合 |

### 4.2 LLM 与数据可靠性

| 名词 | 大白话 | 项目里对应哪里 | 面试怎么说 |
| --- | --- | --- | --- |
| 幻觉 | AI 一本正经编造不存在的内容 | 如果让 AI 直接编景点名，就会出现假地址 | 用真实 API 数据约束生成内容 |
| 幻觉叠加 | 多个 AI 层层编造，错误被放大 | LLM 对 LLM 聊天 | 只有一层做选择，事实数据来自外部 API |
| 候选池 | 先准备好“真实名单”，再让 AI 从里面挑 | 高德 POI 搜索结果进入候选列表 | 行程 Agent 不能自由生成，只能从候选池选 |
| Schema 校验 | 检查返回数据结构对不对 | Pydantic 模型 + 字段校验 | LLM 输出先过结构校验，不合格就修或重试 |
| 质量闸门 | 交付前最后检查一遍 | `quality_agent.py` | 检查坐标、天数、路线闭环，失败自动修复 |
| 有界重试 | 允许失败，但不允许无限循环 | `retry_count <= 3` | 每次带失败原因重试，超上限带警告交付 |
| 降级 | 主方案失败时换备用方案 | 高德天气失败切 Open-Meteo | 外部依赖不能拖垮整个流程 |
| 兜底 | 备用数据源 | Open-Meteo、携程搜索链接 | 核心功能要有失败边界 |
| TTL 缓存 | 数据存一段时间，过期自动失效 | POI 7 天、路线 1 天、天气 30 分钟 | 减少重复请求，同时避免数据永久过期 |

### 4.3 前后端与协议

| 名词 | 大白话 | 项目里对应哪里 | 面试怎么说 |
| --- | --- | --- | --- |
| SSE | 服务器把进度一条条推给浏览器 | `/api/trip/plan/stream` | 长任务用服务端主动推送，适合 30 秒级生成 |
| 轮询 | 前端隔几秒问一次“好了吗” | 没有用，项目用 SSE | 轮询浪费请求，SSE 单向推送更简单 |
| WebSocket | 双向实时通道 | 没有用 | 本项目不需要双向高频通信，SSE 部署更简单 |
| REST | 一问一答的普通接口 | `/api/trip/plan`、`/api/history` | 普通操作用 REST，长任务用 SSE |
| 闭环路线 | 每天从酒店出发，最后回酒店 | 路线质量校验 | N 个景点生成 N+1 段路线，保证能走回来 |
| 意图识别 | 听懂用户想改什么 | 换餐厅 / 降预算 / 加天等 8 类 | 先分类再走专用 handler，避免整段重生成 |
| 多方案 | 同一需求生成几个不同版本 | 人文 / 美食 / 自然 3 套 | 不是只改标题，是重新走完整生成流程 |
| 用户记忆 | 记住用户长期偏好 | SQLite `user_memory` | 下次生成自动带入偏好，减少重复询问 |

### 4.4 工程与部署

| 名词 | 大白话 | 项目里对应哪里 | 面试怎么说 |
| --- | --- | --- | --- |
| 持久化 | 数据存到磁盘，刷新不丢 | 历史行程、用户记忆、聊天会话 | 用 SQLite 持久化，接口层隔离，方便换数据库 |
| 事务 | 要么全部成功，要么全部回滚 | SQLite `with conn:` | 保证写历史时不会写一半 |
| CORS | 允许另一个网站调用你的接口 | FastAPI 中间件 | 前端 Vercel、后端 Railway，需要跨域配置 |
| 环境变量 | 不写死在代码里的配置 | DeepSeek Key、高德 Key、数据库路径 | 敏感信息和运行环境通过环境变量注入 |
| CI/CD | 推送代码后自动测试、自动部署 | GitHub push → Vercel + Railway | 前端和后端分别自动构建，推 main 即上线 |
| Docker | 把后端和环境打包成容器 | Railway 后端 Dockerfile | 后端依赖固定，部署环境可复现 |
| 持久卷 | 容器重启后数据还在的磁盘 | Railway `/data` | SQLite 文件放在持久卷，避免部署丢数据 |

## 6. 高频追问速记

### 6.1 为什么 Agent 之间不直接聊天？

> 直接聊天会变成“LLM 对 LLM”，容易出现语义漂移、成本爆炸、错误无法定位。我用共享状态，每个节点只返回自己负责的字段，由 LangGraph 合并。通信协议就是数据结构，可调试、可保存、可替换。

### 6.2 怎么解决幻觉叠加？

> 三层：第一层，LLM 只能从高德候选池选择，事实来自外部 API；第二层，Pydantic schema 校验结构，缺失字段自动修复；第三层，质量校验检查坐标和路线，不合格带原因重试。

### 6.3 怎么保证状态一致？

> 单一共享状态，节点只写自己的字段，避免互相覆盖；数据库写入用事务；节点边界用 schema 校验；流程有明确的汇合点，不会出现两个节点同时改同一份关键数据。

### 6.4 多 Agent 怎么评估？

> 分四层：单个 Agent 的成功率、链路成功率、产品体验、成本。项目里用 pytest 锁核心逻辑，用质量报告看失败原因，用 SSE 进度定位卡点。

### 6.5 最大的难点怎么讲？

用 STAR，推荐两个：

**难点 A：外部天气接口失败会卡死生成**

背景：高德天气异常时，SSE 一直停在“获取天气”，用户只能刷新。
任务：让外部依赖失败不拖垮整个流程。
行动：天气节点降级到 Open-Meteo，加缓存和 TTL，SSE 增加节点事件。
结果：天气失败仍能生成行程，后端 30 个 pytest 通过。

**难点 B：路线不是闭环**

背景：原来只有“酒店 → 单个景点”，没有景点之间的路线，也没有回酒店路线。
任务：让每天路线形成完整闭环，并支持不同交通方式。
行动：以酒店为起点和终点，生成 N+1 段路线，质量校验加闭环检查。
结果：路线闭合，切换交通方式会重新计算。

## 7. 面试红线

1. 不编造“xx 万用户”“性能提升 xx 倍”，只说代码和测试能验证的数字。
2. 不把“后续想做”说成“已经做了”：登录、CI、Postgres 都是演进方向。
3. 不知道答案时，不要硬编。可以说“这个点我之前没深入，我的思路是先确认边界，再按 XX 方式验证”。
4. 被问不足时，主动说当前短板，并给出演进优先级：移动端验证、CI、用户系统、组件化、Postgres。
5. 讲项目时不要背定义，每讲一个名词都要补一句“在我的项目里对应哪里”。

## 8. 面试前最后 30 分钟清单

1. 能默画一遍架构图。
2. 能完整讲 3 分钟项目介绍。
3. 能说出 3 个“为什么”：
   - 为什么多 Agent？
   - 为什么候选池？
   - 为什么 SSE？
4. 能讲 2 个 STAR 难点。
5. 能说出当前 5 个不足和演进方向。
6. 准备一个演示路径：成都 3 天 → 生成 → 多方案 → 切换交通 → 播放路线 → 记账 → 导出。
